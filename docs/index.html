Title + Abstract

Can a small interpretable model prioritize pages for manual review of an observed decline proxy better than a hand-written rule? We analyzed a 30,000-row anonymized FlyRank internship starter CSV spanning 32 pseudonymous client groups, with trailing 90-day search metrics and a single observed snapshot; the artifact does not state a calendar extraction window. We trained Logistic Regression using five numeric signals and content type, excluded label-derived trend fields and identifiers, and compared the model with a heuristic on the same 20% client-grouped holdout. At the top 50, the model achieved Precision@50 of 0.620 versus 0.320 for the baseline and a test decline base rate of 0.511, while a deliberate leakage test raised Precision@50 to 1.000 when the forbidden `trend_pct` field was added. These results support directional prioritization for human review on this dataset slice, not future forecasting, causal explanations, or a guarantee that refreshing content will recover performance. This is the FlyRank content-refresh case study: when editors face more pages than they can inspect at once, the ranking offers a measured way to order a first-pass review queue while preserving human diagnosis and approval.

1. Introduction / Problem statement

Content and search teams can have more pages to inspect than editors can review in one sitting. A useful first-pass system should help order the queue while leaving diagnosis and decisions to people. This project asks whether a compact, interpretable classifier can rank pages associated with an observed decline proxy more effectively than a transparent heuristic.

The operational decision is narrow: which pages should a reviewer inspect first? It is not “which pages will decline next?” and not “which edit will improve rankings?” A ranked queue can reduce search effort only if its evaluation is honest, its signals are available at review time, and a human can reject a poor recommendation. In the FlyRank content-refresh lane, the practical problem is not to automate edits; it is to help an SEO analyst or editor decide which anonymized pages deserve attention first, then verify measurement, search intent, demand, and page accuracy before proposing any change. The experiment therefore evaluates triage against a transparent rule on held-out client groups, while treating the observed decline label as a snapshot proxy rather than a future outcome.

3. Methodology

Outcome and assumptions

The binary target is an observed decline proxy derived from trend_direction, not an independently verified business outcome. The experiment assumes that the starter file's observed fields are sufficient to test first-pass triage, while recognizing that contemporaneous inputs and labels cannot establish future prediction.

Features and model

The final feature set contains five numeric inputs—days_since_last_update, impressions_90d, ctr, a missing-aware average-position value, and an indicator for missing position data—plus categorical content_type. Numeric missing values are median-imputed and standardized; categorical missing values are imputed with the most frequent value and one-hot encoded. Logistic Regression is the learned ranking model. The seed is 42.

Baseline

The transparent rule baseline combines percentile-ranked visibility (40%), freshness risk (30%), position opportunity weighted by visibility (25%), and content-depth gap weighted by visibility (5%). It is a heuristic comparator, not a trained model, and it does not use label-derived fields. The baseline and model are scored on the same held-out rows using Precision@K.

Validation design

An 80/20 GroupShuffleSplit holds out entire clients, with seed 42. The run recorded 23,837 training rows from 25 clients and 6,163 test rows from 7 clients, with zero client overlap. The primary metric is Precision@50 because the artifact is a short review queue. Precision@10, @20 and @100, ROC-AUC, average precision, test base rate and lift are reported as supporting context.

Leakage checks

The final feature list excludes the target, trend_direction, trend_pct, both identifiers, and recommendation/model-output fields. As a deliberate negative control, a separate throwaway model was given trend_pct; its Precision@50 rose to 1.000 and ROC-AUC to 0.955, compared with 0.620 and 0.563 for the honest feature set. This artificial gain is evidence of label leakage, not a result to deploy.

4. Results

On the client-grouped test set, the Logistic Regression ranking outperformed the reproduced rule baseline at each reported cutoff. The test base rate was 0.511, so Precision@50 of 0.620 corresponds to 1.21× lift over that base rate. ROC-AUC was 0.563 and average precision was 0.555: useful context that also cautions against describing the model as a strong general-purpose classifier.

Validation design matters

The Week 6 audit compared the same Logistic Regression under a naive row-random split and a client-grouped holdout. The row-random split had 31 clients overlapping between train and test; the grouped split had zero. Precision@50 was 0.580 for row-random and 0.620 for grouped holdout, while ROC-AUC changed from 0.607 to 0.563. The grouped result is the more relevant estimate for unseen-client use even though its Precision@50 happened to be higher in this run.

Interpretation. The observed result is promising enough to test as a review aid, but modest AUC, a small number of held-out client groups, and the contemporaneous proxy label limit any broad claim of generalization.

5. Evidence-backed insights

The current notebook run produces four review findings from the client-grouped holdout. They are deliberately framed as measured triage evidence, not claims about future search performance.

  1. The learned ranking beats the rule at all reported queue sizes. Precision@10 is 0.500 vs 0.400; Precision@20 is 0.550 vs 0.400; Precision@50 is 0.620 vs 0.320; and Precision@100 is 0.600 vs 0.310. Action: keep the learned ranker as a candidate ordering aid and compare it with the rule on every new evaluation.
  2. The evidence supports top-K triage, not a strong general-purpose classifier. Precision@50 is 0.620 against a 0.511 test proxy rate (1.21× lift), while ROC-AUC is 0.563 and average precision is 0.555. Action: choose K from actual reviewer capacity and validate on a future time window; do not interpret scores as calibrated probabilities of recovery.
  3. Client grouping reduces a common validation leak, but unseen-client evidence is limited. The split contains 23,837 train rows across 25 clients and 6,163 test rows across 7 clients, with zero client overlap. Action: repeat the experiment across more client groups and a future time period before operational use.
  4. Label leakage can make a weak model appear excellent. The invalid negative control that adds trend_pct reaches Precision@50 1.000 and ROC-AUC 0.955, compared with 0.620 and 0.563 for the honest feature set. Action: keep label-source fields excluded and rerun leakage checks whenever the target or feature frame changes.
Decision boundary. A high score means “inspect this record earlier,” not “make this edit” or “traffic will recover.” The action playbook remains human-reviewed.

6. Limitations & honest framing

  • Not the full warehouse. This experiment uses a 30,000-row starter CSV, not the broader 79-million-row production dataset described in the assignment context.
  • No declared calendar window. The inspected starter artifact does not provide a reliable extraction-date range in the notebook outputs. Only the trailing 90-day metric window is explicit.
  • Snapshot label, not future forecast. The label is derived from an observed trend field and the inputs come from the same snapshot. No forward-in-time outcome test is shown.
  • Not causal. No intervention or controlled test establishes that editing or refreshing a page causes recovery.
  • Limited client coverage. The grouped test set contains 7 clients; performance may vary substantially across clients, verticals, and time periods.
  • Proxy and metric limitations. A “down” label is not a complete definition of business harm. Precision@K depends on K and label prevalence; ROC-AUC is only 0.563, and scores should not be interpreted as calibrated success probabilities.
  • Not production-ready. The queue does not include a measured ROI, reviewer study, live monitoring results, or a deployment control system.

The strongest supported claim is: On this anonymized starter dataset, Logistic Regression ranked the observed decline proxy more effectively than the reproduced rule at the evaluated top-K cutoffs on a client-grouped holdout, supporting further testing as human-review decision support.

7. Ranked recommendations: the action playbook

These are ordered review priorities, not automatic edits. Reason codes are transparent heuristics to start diagnosis; they are not causal explanations of the model.

PriorityReason code / cueFirst human checkPossible next step only if verified
1NO_POSITION_DATACheck reporting freshness, indexation and missing data.Fix measurement or investigate indexing before editing content.
2LOW_CTRCompare intent, current snippet/title and search-results context.Test a truthful snippet/title revision with a defined success measure.
3LOW_VISIBILITY + stale candidateVerify factual accuracy, intent match, internal links and competing pages.Draft a scoped refresh proposal for editorial approval.
4LOW_VISIBILITYDiagnose indexing, competition, intent and site architecture.Investigate first; do not assume a rewrite is the answer.
5LOW_DEMAND_OR_REACHCheck seasonality, demand, indexation and page purpose.Defer or monitor if low demand is expected.
6STALE_CONTENT_CANDIDATECheck whether facts or user needs have materially changed.Update only the specific outdated sections if confirmed.

Human review and no-go rules

Before action, confirm the page and data freshness, inspect measurement and indexation, verify facts and search intent, check seasonality and competing pages, and write a proposed change plus a success metric. A reviewer must approve, defer or reject the action; no change is a valid outcome.

  • Do not auto-publish or auto-rewrite content.
  • Do not automatically change URLs, redirects, canonicals or site-wide links.
  • Do not promise ranking or traffic recovery.
  • Do not use the score alone to allocate budget or claim causality.

Monitoring and retraining

  • Review monthly as a research prototype; record data version, label definition, metrics, reason-code mix and human overrides.
  • Investigate if key-input missingness rises by 10 percentage points or the reason-code mix shifts sharply.
  • Pause the prioritization claim if Precision@50 lift is at or below 1.0 on a fresh evaluation for two consecutive checks.
  • Revalidate after any schema, tracking or label change. Retrain only with appropriately timed new data and a fresh grouped/time-aware evaluation against a simple baseline.

9. Presentation outline

The same evidence can be presented in a short six-slide review. Keep the top-K results and leakage control visible, and make the handoff to human review explicit.

  1. Problem and decision. Explain the page-review bottleneck and the narrow goal: rank which records to inspect first, not predict guaranteed recovery.
  2. Data and target. Describe the 30,000-row anonymized starter snapshot, the observed trend_direction == "down" proxy, and the public-safe reporting boundary.
  3. Method and validation. Compare Logistic Regression with the transparent rule baseline; show the client-grouped 80/20 split, seed 42, 25 train clients, 7 test clients, and zero client overlap.
  4. Results at reviewer capacity. Show Precision@10, @20, @50 and @100 beside the rule and test proxy rate; call out Precision@50 of 0.620 vs 0.320.
  5. Leakage and limitations. Show why trend_pct is invalid; note ROC-AUC 0.563 and limited coverage of seven held-out clients; clarify the snapshot label is not a future outcome.
  6. Action playbook and next experiment. Walk through measurement, indexing, intent, CTR, visibility and freshness checks; propose future-window validation and state the no-automatic-edit rule.

Suggested talk track: problem → data → method → evidence → risk → action. Use the metrics generated by the latest notebook execution if data or code changes.
